# Hydration gate spec

**Purpose:** turn a newly landed table into approved, owner-reviewed metadata in `gov`, projected to Unity Catalog.

## Flow (one job run per table)

1. **Guard** — compute `schema_hash` = sha256 of sorted `(column_name, data_type)` pairs. If a row in `gov.column_profiles` has the same table + hash AND every column is *covered* → exit, zero LLM calls, nothing written to any governance table. The run still writes its `gov.hydration_runs` row (status `skipped`, `guard_hit` true, `llm_calls` 0), so a guard exit can be seen. A column is covered when it has approved metadata, or a pending (`proposed`) proposal from a run with the same schema_hash. Otherwise continue, proposing only uncovered columns (new table, schema change, or rejected proposals). **Eval/force mode** (`--force`): skip the guard, propose every column, and write profiles and proposals under a caller-supplied `run_id` (one id shared by every table in an eval run), so a prompt or model change is measured with real LLM calls. Eval proposals get status `eval`: the guard and approve read only `proposed` rows, so an eval never enters the review queue or covers a column. Re-running an eval table under the same `run_id` replaces its rows. Every hydration attempt, forced or not, writes `gov.hydration_runs` rows: `running` when it starts on a table, then `skipped`, `succeeded` or `failed`. A failure on one table does not stop the others; the job exits non-zero at the end.
2. **Profile** — per column: data_type, null_pct, distinct_pct, avg_length, pattern_hits (≥ 80% of non-null values match: email, uk_ni_number, postcode, phone, sort_code, iban, iso_date, currency_amount), any_pattern_hits (at least one value matches), existing scan result if available. Write to `gov.column_profiles`. No raw values stored or sent anywhere; `sample_hash` only.
   **Noise names first** — a column whose every token (split on `_`, case changes and digits) is in `noise_tokens` (abbreviations.yaml) or a bare number, with at least one noise token, is proposed in code: method `rule`, `NO_MATCH`, confidence 1.0, sensitivity from the normal floor. It never reaches fuzzy or the LLM, so the answer is deterministic and costs no tokens. `weak_noise_tokens` (`ref`, `user`) count as noise only next to another noise word: `ref`, `user_ref`, `ref_1` are not noise, `LEGACY_REF_2` and `user_def_3` are. Exceptions — the column goes on to fuzzy/LLM when: a value pattern covers ≥ 80% of values (`pattern_hits`); any value hits a PII pattern (`any_pattern_hits` ∩ email/uk_ni_number/phone/postcode/sort_code/iban); or it looks like free text (`avg_length` > 30 and `distinct_pct` > 50). The LLM's free-text and partial-PII sensitivity rules then apply. A reviewer who rejects a rule proposal must edit it instead: a re-run gives the same rule answer and never asks the LLM. `col_cd` is not noise (`cd` = code); `Col17`, `user_def_3`, `LEGACY_REF_2` are. Approve never auto-accepts it (NO_MATCH).
3. **Expand + fuzzy match** — expand abbreviations (`src/gates/hydration/abbreviations.yaml`), score against term names + synonyms with `rapidfuzz.fuzz.token_set_ratio`. Abbreviations are expanded on both sides (column name and term names/synonyms). Column names first drop `ignore_tokens` (abbreviations.yaml): currency codes (`gwp_gbp` → `gwp`), and, with `strip_trailing_digits`, a digit run glued to a known word in the same name part (`addr_line1` → `addr line`; known = an abbreviation key or a key's whole one-word expansion). Unknown words keep their digits (`acct_last4`, `Col17`) and a digit that is its own part is kept (`LEGACY_REF_2`), so noise names stay noise. If the ignore rules removed anything and a single token is left (`gwp_gbp` → `gwp`, `Value17` → `value`), the column never fuzzy-accepts: it goes to the LLM, which sees the original name. Score ≥ `fuzzy_accept` (default 90) and strictly higher than every other term → proposal with method `fuzzy`, confidence = score/100, no LLM. A tie at the top (common with token_set_ratio: a bare `status` scores 100 against every `<x> status` term) goes to the LLM. An abbreviation may have several readings (e.g. `exp`: expiry/exposure/expense); each reading is scored and the best kept, but a column containing an ambiguous token never auto-accepts on fuzzy and goes to the LLM with every reading shown in its expanded name. Fuzzy accept also needs full column-token coverage: in the column reading × term name/synonym reading pair that gives the top score, every column token must appear among that target's tokens (the target may have extra tokens; the column may not), so `tmp_col` never auto-accepts against the synonym `col`. Otherwise keep top 5 candidates. Candidates with equal scores are ordered by overlap with the table name's tokens (singularised: `payments` → `payment`), then term_id, so a bare `amt` in `payments` puts `payment_amount` in the five; the tie-break never turns a tie into a fuzzy accept.
4. **LLM propose** — one call per table, all unresolved columns batched. The prompt version is a job parameter (`prompt_version`, `propose_v<N>`); proposals record it. A prompt whose USER section contains `{{table_columns}}` also gets every column name in the table (names only, no values or stats) so generic names can take meaning from their neighbours; prompts without the placeholder get exactly the input they were released with. Input per column: name, expanded name, profile stats (incl. avg_length), pattern hits and any_pattern_hits, 5 candidate terms (id, name, definition, sensitivity, fuzzy_score). Output: strict JSON per column `{column, term_id | "NO_MATCH", description, sensitivity, confidence, rationale}`. `term_id` must be one of the candidates or `NO_MATCH`; anything else is rejected and logged. Temperature 0.
5. **Write proposals** — `gov.term_proposals`, status `proposed`, with method, model, prompt_version, tokens.
6. **Approve** — owner (or demo auto-rule) sets status `accepted` / `edited` / `rejected`. The auto-rule accepts only when all three hold: (1) a term was proposed — `NO_MATCH` never auto-accepts; (2) confidence ≥ 0.8; (3) no PII pattern (email, uk_ni_number, phone, postcode, sort_code, iban) hit any value of a column whose term is not `pii` — `pattern_hits` (≥ 80% of values) or `any_pattern_hits` (at least one value), so free text with a few emails under a confident non-`pii` term goes to review. Everything else goes to human review. Accepted/edited rows upsert into `gov.approved_metadata`. An approved column is corrected only by a `revise` decision on its newest decided proposal: same identity and approver rules as an edit, sensitivity re-floored from that proposal's profile, the proposal becomes `edited`, its golden candidate is updated, and the replaced row is kept in the audit log. Never by hand SQL on `approved_metadata`. Every decision → `gov.audit_log`. Edits → appended to `gov.golden_candidates`.
   The owner sets the product's permitted uses at approval (H15): one row per use, giving
   use_code (controlled list), approval (standing / approval_required / prohibited), optional
   conditions, and max_term_days (default 365). Approval is refused without at least one row.
   The owner INSERTs rows into `gov.permitted_use_inputs`; the approve job applies them first, through the audited
   `set_permitted_use` path (committer must be a table approver, as for review decisions; use_code from the
   `permitted_use_codes` list). A change writes a new version and retires the old one in one MERGE (audit
   `permitted_use_set`, before/after); the same values again change nothing. With no active `permitted_uses` row for
   the table, manual accept/edit decisions are refused and the auto-rule accepts nothing; reject and revise are never
   blocked (a correction must not wait). Insert the permitted uses first, or with the decisions.
7. **Apply** — project `approved_metadata` to UC, one table per run, as the CI service principal: column comment = `description` (NULL clears it), governed tag `<tag_prefix>_sensitivity` = `sensitivity`, tag `<tag_prefix>_business_term` = `term_id` (unset when NULL). `tag_prefix` is a bundle variable, default `gg`. Apply compares gov with the current UC state on every run (UC is read only to find the difference, never as truth), so a hand-removed tag is restored and a revised column loses its old tags. It manages only these two keys. Our keys on a column with no approved row are reported, not removed. An approved row that differs from its newest approve audit event (changed by hand SQL) is refused: audit `apply_refused`, no UC change, no stamp. Order per column: audit `apply_started` (deterministic event_id over the change and the row's current `applied_to_uc_at`, so a crashed run's replay adds no duplicate and a later repair of the same drift is a new event), then UC statements, then the outcome: `applied_to_uc` and stamp `applied_to_uc_at`, only if the row still equals what was projected (a row approve changed meanwhile stays unstamped); or, if a statement fails, `apply_failed` (id from the change and the error class, so retrying a persistent failure adds no rows) and no stamp. A failing column does not stop the others; the run then exits non-zero. Idempotent: a second run plans zero statements and writes nothing.
   **When it runs** (Q20; signed off 10 Nov): as the second task of the `approve` job, for the same table, only after approve succeeded, so an approve or revise reaches UC in the same run. There is no separate apply job (two applies on one table could race and leave UC behind a stamped row); to repair drift, run `approve` again (approve, then apply). That run also applies any pending owner decisions and permitted uses for the table and the auto-rule, so check `v_hydration_queue` for the table first; a repair-only mode (apply without decisions or auto-rule, still in this job) is a later item. The job queues a second trigger rather than skipping it. When the table does not exist or is not visible to the job principal, approve still applies reject and revise (step 6: a correction must not wait), leaves accept/edit decisions and permitted-use inputs pending, plans no auto-rule, then fails, so apply does not run and a revised row stays unstamped (fail closed). Failure semantics: if approve fails, apply does not run; if apply fails for a column, the row stays unstamped, the product is not ready for the grants generator, and the next `consumption_apply` revokes its grants (fail closed). Between the approve task committing a revise to `pii` and the apply task tagging the column (task start-up plus statements, in every run), and until a failed apply is repaired, the column is `pii` in gov but untagged in UC, so an existing grant reads it unmasked; the job's failure email (`notify_on_failure`, set per target, empty on dev) is how someone finds out, so every non-dev target must set it (none does yet: today nobody is told).

## Config seams

- `llm_provider`: `ai_query` (Databricks serving endpoint name) or `openai` (OpenAI-compatible base URL + key from a secret scope).
- `catalog`, `raw_schema`, `gov_schema` from bundle variables.
- `tag_prefix` (default `gg`): UC tag keys are `<tag_prefix>_sensitivity` and `<tag_prefix>_business_term`.

## Sensitivity classes

`public` < `internal` < `confidential` < `pii`. Code enforces the floor: final sensitivity = max(pattern floor, chosen term's sensitivity, proposed sensitivity). Pattern hits on email / NI number / phone / postcode / sort code / IBAN give a `pii` floor. The model may raise a class, never lower it. `public` only if the chosen term is `public`; otherwise the floor is `internal` (so a `NO_MATCH` proposal is never `public`). Prompt rule (v1): long, high-distinct text columns are at least `confidential`, `pii` if any PII pattern appears in any value.

## Known limitations

- **Confident wrong term on a pattern-less personal column.** A name, date of birth or address column has no value pattern, so no pattern floor fires. If the proposer picks a wrong, non-`pii` term at confidence ≥ 0.8, the auto-rule accepts it at that term's sensitivity. Measured by `pii_recall` in the eval (specs/eval.md); not prevented by code.

## Out of scope for the skeleton

UI (the client's own review tool replaces the approve step on site), validation rules, multi-metastore push.
